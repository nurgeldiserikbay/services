# Спецификация v1 — согласованность заявок, календаря и уведомлений

**Статус:** proposed implementation contract (не реализовано). **Дата:** 2026-11-02.  
**Основания:** ADR-0003 (простые заявки), ADR-0004 (отмены и надёжность), ADR-0005 (гостевой доступ), `docs/architecture/modular-boundaries.md`. Если возникает противоречие, ADR имеет приоритет; изменение решения требует отдельного ADR.

## 1. Границы и словарь

- `ServiceOffer` имеет одного `seller`: самостоятельный `ProfessionalProfile` **или** `Organization`. Контекст страницы фиксируется в заявке и никогда не изменяется из-за смены места работы исполнителя.
- `ServiceRequest` — простое обращение к продавцу, **не коммерческое предложение**. Никаких Quote, платежей, торгов, обязательного заполнения цены или контроля стоимости.
- Телефон/WhatsApp — внешняя связь, **не подтверждённая платформой запись**; продавец самостоятельно отмечает занятость. Не приписывать платформе результаты внешних разговоров.
- `preferred_start_at` — пожелание клиента, `scheduled_start_at` — согласованная обеим сторонам дата/время. Пожелание само по себе не активирует штрафы.
- Календарь опционален. При отсутствии точных слотов заявка остаётся доступной, а UI не обещает гарантированную свободную запись.
- `performer` — необязательный мастер, который оказывает услугу от имени компании; seller при этом **остаётся компанией**.

## 2. Инварианты переходов

| Исходное состояние | Действие | Результат | Обязательное условие |
| --- | --- | --- | --- |
| Нет заявки | Создание гостем/клиентом | `PENDING` | Offer активен, канал заявок разрешён, anti-spam и auth/guest capability |
| `PENDING` | Принять продавцом | `ACCEPTED` | Seller ACL, один победивший переход; согласованность слота |
| `PENDING` | Отклонить продавцом | `DECLINED` | Seller ACL, причина необязательна |
| `PENDING` | Отозвать клиентом | `CANCELLED` | Автор или scoped guest capability; без штрафа |
| `ACCEPTED` | Отменить любой стороной | `CANCELLED` | Проверка actor и snapshot; два notification intent |
| `ACCEPTED` | Подтверждённое оказание | `COMPLETED` | Только поддерживаемое действие, без придумывания auto-complete по таймеру |
| Финальное состояние | Повторить переход | Без новых эффектов | Вернуть текущий ресурс или конфликт 409 |

`DECLINED`, `CANCELLED`, `COMPLETED` — терминальные для базового MVP. Повторное обращение создаётся отдельно. Изменения времени после принятия — отдельный согласованный процесс, нельзя молча перезаписать snapshot и задним числом наказать клиента.

## 3. Как принимать заявку при конкуренции

1. Каждая мутация использует идентификатор операции/Idempotency-Key, связанный с actor, route и canonical body hash; повтор с тем же содержимым возвращает прежний результат, с другим — конфликт.
2. Сервер проверяет права на seller/request **в момент записи**, не только при открытии страницы. Для гостя — проверять точное scope capability; токены хранить хешированными и ограничивать по времени/назначению.
3. Для перехода использовать одну атомарную транзакцию: заблокировать `ServiceRequest` либо optimistic compare-and-swap `WHERE status = PENDING`, проверить слот и занятость, изменить статус, создать событие и outbox.
4. Два конкурентных решения продавца (accept/decline) не могут оба победить. Проигравший получает 409 + актуальное состояние, не «успех» по устаревшему UI.
5. Двойной tap и повтор из-за потери сети не должны создать два заказа, два штрафа, два release busy или два логических события; ключи идемпотентности ограничены actor+операцией и имеют документированный TTL.
6. Если клиент отменил `PENDING` одновременно с принятием, побеждает **первый закоммиченный переход**. При принятии первым последующая отмена обрабатывается по правилам `ACCEPTED`, с применением политики только если есть зафиксированное время. Клиент видит актуальный итог, а не ложное подтверждение предыдущего состояния.

## 4. Занятость и контексты мастера

- Прежде чем считать слот доступным, применить allocation в соответствующем личном/корпоративном контексте, пересечения активных platform-known `BusyBlock`, таймзону IANA и DST-случаи.
- В конкурентном сценарии два продавца могут претендовать на одного мастера; при **bookable guaranteed slots** пересечение подтверждённых занятостей одного мастера запрещено DB-инвариантом/транзакционной блокировкой. Нельзя обещать гарантию, если продавец не ведёт свой календарь или сторонние записи неизвестны.
- Корпоративный ACL открывает детали только своей заявки. Другому seller разрешается максимум «занято», не источник блокировки, имя клиента, контакты или цена.
- Подтверждение датированной заявки создаёт или связывает занятость в той же транзакции; отмена освобождает только принадлежащую ей платформенную занятость, не произвольную ручную или чужую.
- Если нет выбранного мастера или сервис работает без календаря, не создавать вымышленную блокировку его персонального расписания.
- Отправка заявки не бронирует слот автоматически; soft hold, если когда-нибудь потребуется, решать отдельным ADR.

## 5. Правило отмены и надёжности

Сервер использует immutable `CancellationPolicySnapshot` из ADR-0004: seller, версия правила, `scheduled_start_at`, timezone, `free_cancel_before_minutes`, вычисленный дедлайн, время принятия. Deadline вычисляется в UTC и представляется человеку в локальном timezone; сервер — источник истины.

- `PENDING`: нет влияния на надёжность.
- `ACCEPTED`, но нет подтверждённого `scheduled_start_at` или достоверного уведомления правила: клиенту **не** применять автоматическую позднюю санкцию.
- `ACCEPTED`, согласованное время, клиент зарегистрирован: ранняя отмена без penalty; поздняя — один `ReliabilityEvent` согласно ADR-0004 и его исключениям, включая grace window позднего принятия.
- Гость не получает постоянный `customer_reliability`; нельзя позже автоматически присвоить старое гостевое нарушение новому аккаунту.
- Отмена продавцом влияет на `provider_reliability` фактического независимого профиля или организации, а не автоматически мастера компании.
- Любая отмена создаёт **ровно два логических NotificationIntent** (инициатору и второй стороне); отсутствие email/SMS не отменяет доменное действие.
- `ReviewRating` за качество услуги никогда не изменяется отменой. No-show, ручные исключения и апелляции — отдельно с доказательствами и аудитом.

## 6. Transaction + outbox

Для **успешной отмены** одна транзакция фиксирует:
1. смену статуса и `CancellationEvent` (с actor, причиной/типом, policy snapshot и временем);
2. освобождение только platform-owned busy lock, если он был;
3. не более одного применимого `ReliabilityEvent` (или явное решение «не применять»);
4. `DomainOutboxEvent` и **ровно два** уникальных `NotificationIntent` с независимыми recipient/scope и dedupe key.

Commit предшествует отправке сообщений. Фоновый worker доставляет at-least-once с дедупликацией, backoff, retries и dead-letter/reconciliation. Доставка может повторяться технически, но не должна создавать повторное бизнес-уведомление в интерфейсе. Отсутствие доступного канала отмечается как delivery status, а не откат отмены.

Для создания/принятия/отклонения заявки применяется тот же outbox принцип, но количество получателей определяется соответствующим бизнес-событием; правило «ровно два» относится именно к отменам.

## 7. Ошибки API и UX

| Код/ситуация | Сервер | Клиент |
| --- | --- | --- |
| 400/422 некорректное время/timezone, поля | Структурированная ошибка валидации | Показать конкретные поля, не повторять молча |
| 401/403 нет сессии/прав/guest scope | Не раскрывать данные чужой заявки | Без приватных деталей, дать корректный путь доступа |
| 404 недоступный объект | Не раскрывать существование чужого объекта | Нейтральное сообщение |
| 409 устаревший статус/занятый слот/не тот payload для key | Актуальный статус и machine-readable reason при наличии прав | Обновить карточку; не отправлять новый запрос автоматически |
| 429 rate limit OTP/гостевых заявок | Rate-limit без раскрытия account existence | Показать retry-after |
| Timeout после записи | Повтор по **тому же** idempotency key | Показать проверяемый pending state, затем факт из API |
| Уведомление недоставлено | Delivery retry / статус | Не объявлять доменную операцию неуспешной |

UI блокирует повторную кнопку на время мутации, но **не** считает это защитой от дублей; сервер идемпотентен. Abort устаревшего GET допустим, **отмена HTTP-запроса браузером не гарантирует отмену серверной мутации**.

## 8. Приёмочные тесты перед реализацией

- Два одинаковых POST (включая parallel) создают одну заявку и один набор событий; mismatch idempotency body возвращает 409.
- `accept` и `decline` одновременно: только один финальный результат; другой 409.
- `cancel pending` против `accept`: один сериализованный результат, корректная политика последующей отмены.
- Два `accept` на несовместимые гарантированные слоты одного мастера: не более одного успеха.
- Отмена при одновременном повторе: один `CancellationEvent`, два и только два intent, максимум одно событие надёжности.
- Отмена `PENDING` и `ACCEPTED` без agreed time не снижает customer score.
- Late cancellation после согласованного срока применяет penalty только авторизованному клиенту и с исключениями ADR-0004.
- Отмена компанией не ухудшает показатель мастера как независимого продавца; не изменяет звёзды отзывов.
- При worker crash после отправки, до отметки delivery: повтор безопасен; после DB commit при отключённом worker отмена остаётся действительной.
- Из корпоративного контекста невозможно получить личные busy детали, чужого клиента или поменять seller.
- Смена timezone, DST gap/fold, перенос продавцом и смена правила после accept не ведут к скрытому изменению penalty.
- Гость с capability другого scope или истекшим токеном не получает доступ к заявке.
- Комбинация offline/retry/double-click демонстрирует фактический результат, а не призрачную заявку.

## 9. Вопросы для уточнения непосредственно перед backend implementation

Нужны явные решения и синхронизация с OpenAPI/Prisma по: точным status enum и переходу `COMPLETED`; времени жизни/хранения idempotency records; способу реального SQL exclusion constraint на busy ranges; согласованию слота при заявке без расписания; событию изменения времени и обновлённому snapshot; правилам хранения и анонимизации уведомлений; machine-readable error codes и механизмам reconciliation.

**Граница готовности:** этот текст задаёт ожидаемые инварианты и негативные сценарии, но не заменяет конкретные миграции PostgreSQL, OpenAPI operation bodies, реальные интеграционные тесты, legal sign-off и UX review.
