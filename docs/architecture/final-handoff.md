# Services — финальная передача технического задания

**Версия:** ТЗ v1.0 (содержание утверждено, техническая проверка — отдельный gate). **Дата:** 2026-11-02.  
**Граница:** документ фиксирует требования к разработке, но не утверждает, что приложения уже реализованы, протестированы или готовы к публикации.

## Итоговое решение

**Product scope: FROZEN FOR MVP.** Владелец продукта подтвердил ADR-0006. Новых продуктовых вопросов, препятствующих декомпозиции разработки, не выявлено; изменения требований оформлять новыми ADR с влиянием на API/схему/UX.

### Продукт
- Открытый глобальный каталог услуг; локальная выдача по умолчанию, ручная смена географии, публичные страницы без регистрации.
- Специалист и компания — разные продавцы. Заявка, созданная в представлении компании, принадлежит компании. Личные данные и отзывы специалиста нельзя присваивать компании.
- Контакт по телефону/WhatsApp или простая заявка. Отсутствуют торги, сметы, обязательные цены и платежи; календарь необязателен.
- `PENDING → ACCEPTED/DECLINED → COMPLETED/CANCELLED` с отдельными конечными статусами отмены, идемпотентностью и аудитом.
- **ADR-0006 ACCEPTED:** желаемое время не равно согласованному; дата считается подтверждённой только после явного подтверждения второй стороной. При отсутствии согласованного времени автоматический клиентский штраф недопустим.
- Продавец задаёт срок отмены по услуге; поздняя отмена зарегистрированного клиента при выполнении условий влияет только на его надёжность; отмена продавца — на надёжность продавца, не на звёздные отзывы. При отмене — два логических уведомления.
- Гостевой доступ строго на одну заявку, с проверкой контакта; `MANAGE_SCHEDULE` нельзя заменить `READ_CANCEL`.

## Статусы: не подменять один другим

| Показатель | Статус | Что необходимо |
| --- | --- | --- |
| Бизнес-требования MVP | **Содержательно зафиксированы** | Не менять без ADR |
| Документированная архитектура и API | **Подготовлены как reference** | Проверка совместимости и миграций при реализации |
| HTML ↔ Markdown | **Исправлено в main** | Контроль через docs workflow на конечном SHA |
| OpenAPI/Prisma/PostgreSQL CI | **Результат последнего main SHA не подтверждён** | Получить полный успешный workflow run для итогового коммита |
| Реальная безопасность и гонки | **Требуются интеграционные тесты** | Реализация в `services-back` |
| UX, kk/ru и мобильный E2E | **Приёмка на этапе реализации** | Реальные браузеры и устройства |
| Право и публикация по географиям | **Вне рамок финализации ТЗ** | Отдельный market-specific review до запуска |

**Решение по завершению ТЗ:** документацию допустимо считать **content-complete** и брать в разработку. Нельзя присваивать статус `contract-validated` / `implementation-ready` без реальных свидетельств CI, и нельзя называть код production-ready по факту наличия этого документа.

## CI, воспроизводимость, доказательства

На `main` после изменений должны выполняться:
```bash
npx --yes prisma@6.19.0 validate --schema contracts/prisma/schema.prisma
npx --yes @redocly/cli@1.34.5 bundle contracts/openapi.yaml -o /tmp/services-openapi-bundled.json
node scripts/check-api-contract.mjs /tmp/services-openapi-bundled.json
node scripts/build-site.mjs
git diff --exit-code -- index.html
node scripts/check-docs.mjs
```
PostgreSQL проверки — только с одноразовой test database через `.github/workflows/contracts.yml`, включая применение `constraints.sql` и `smoke.sql`. В каждом PR фиксировать SHA, URL работы CI, тестовое окружение и результат. Предупреждения о deprecated npm-пакетах сами по себе не являются ошибкой YAML.

## Порядок передачи команде

1. Начать с `DOC-02`, `BE-01`, `OPS-01` из плана реализации; подтвердить схему и базовые API-типы.
2. Реализовать slices каталога и простой заявки; затем отмены и необязательное согласование времени.
3. Завершить независимые разрешения ролей, guest token, компанию/мастера, outbox и конкурентные транзакции.
4. Применять acceptance-checklist к каждой вертикальной функции, включая негативные ACL и retries; фронт не определяет безопасность.
5. Проверить country/category launch rules, политику данных, работоспособность на реальных устройствах перед публичным выпуском.

## Незакрытые технические риски (не новые продуктовые вопросы)

- Убедиться, что `CancellationSnapshotRevision` и текущий snapshot обновляются атомарно и аудит фиксирует использованную ревизию.
- Проверить уникальность и длительность гостевых возможностей, OTP rate limits, отсутствие escalation и cross-request IDOR.
- Зафиксировать семантику ответа на повторное Idempotency-Key и восстановление после сбоя/время жизни записей.
- Проверить миграционную совместимость с реальным `services-back` и SQL invariants на PostgreSQL.
- Сделать корректные состояния времени в UX, включая подтверждение второй стороны, отсутствие календаря, конфликт и отмену.
- Проверить regenerated HTML и все контрактные checks на актуальном SHA.

**Остальные вопросы про реализацию не блокируют завершение текста ТЗ; они входят в обязательную Definition of Done разработки.**
