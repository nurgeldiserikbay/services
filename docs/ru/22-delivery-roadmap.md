# 22. План разработки: эпики, зависимости, релизы и DoD
> План v0.2. Оценки в неделях не фиксируются до оценки трудоёмкости; указаны зависимости и критерии выхода. Все изменения должны отражаться в сервисной документации.

## Четыре репозитория
| Репозиторий | Базовый стек / ответственность | Границы |
| --- | --- | --- |
| services | Markdown как source of truth, HTML-генерация, OpenAPI, ADR, acceptance | Нет runtime бизнес-логики |
| services-back | NestJS, Prisma, PostgreSQL, REST, workers | Не владеет клиентскими UI |
| services-admin | Next.js, internal administration, generated API client | Не прямой доступ к БД |
| services-front | pnpm workspace, Next.js web/PWA, React+Vite+Capacitor mobile, shared UI | Нет самостоятельных доменных правил |

## Фаза 1 — workspace foundation / параллельные работы
**Backend:** NestJS skeleton, Config, Auth, Prisma migrations, audit/outbox, CI, tests.
**Frontend:** Next.js+PWA, mobile Capacitor skeleton, shared UI/i18n, typed client, auth adapter, CI.
**Admin:** Next.js skeleton, privileged auth, roles, shell, basic moderation placeholders.
**Docs:** ADR по полиморфным ссылкам, режимам авторизации, upload, data residency.
**Выход:** приложения стартуют локально, есть staging, healthcheck, CI и smoke; нет fake «готовых» страниц.

## Фаза 2 — идентичности и профессиональные профили
**Backend:** User/Person, canonical professions, uniqueness, profile lifecycle, revisions, publish APIs.
**Frontend:** onboarding, 1-profile-per-profession, builder MVP, versions, account workspace.
**Admin:** справочник профессий, жалобы на профили и просмотр статуса.
**Выход:** создание/архив/восстановление/дубли с race tests; публичные и приватные режимы корректны; kk/ru.

## Фаза 3 — компании и конкретные услуги
**Backend:** Organization, Location, roles, Affiliation, ServiceOffer, ServiceAssignment with consent.
**Frontend:** организация, филиалы, команда, приглашения, список услуг и отображение текущего места работы.
**Admin:** спорные связи, проверка организаций, аудит.
**Выход:** одна профессия работает в двух компаниях без передачи собственности, назначения точны по услуге, прошлые связи не теряются.

## Фаза 4 — поиск, заявки, отзывы
**Backend:** Search, simple ServiceRequest accept/decline/cancel, optional availability blocks, Experience, Review target integrity, SavedItems, Follow, Notifications.
**Frontend:** каталог, карточки, заявка, история, два отзыва, подписки.
**Admin:** очередь жалоб, ревью отзывов, апелляции.
**Выход:** полный сквозной happy path, error/denied/race variants, реальный мобильный smoke.

## Фаза 5 — безопасность, запуск пилота
Data protection review, consent, audit, backup/restore drill, on-device Android/iOS, accessibility, load tests, abuse, anti-spam, app-store policies, SEO, observability.
**Выход:** staging sign-off, контроль незавершённых заявок и жалоб, эксплуатационный ответственный, rollback rehearsal, публикация пилота.

## Фаза 6 — retention/монетизация (после пилота)
Календарь, промокоды, loyalty, расширенные уведомления, Pro/Business, платное продвижение, аналитика — только по метрикам спроса и отдельным ADR/контрактам.

## Параллельные потоки
- Track A backend identity/profile → org/offers → booking/reviews.
- Track B front foundations → profile/builder → search/booking.
- Track C admin shell → verification/taxonomy → review moderation.
- Track D docs/contracts/QA → contract gate, acceptance, regression.
**Интеграция:** сначала docs + OpenAPI, затем backend contract tests, затем generated front/admin clients. Каждая команда имеет ownership и короткие PR.

## Definition of Ready
Задача имеет ID, сценарий, API/DTO, правила доступа, состояния, локализацию, UX, зависимость и тест приёмки. Если это не определено — не начинать изобретать правила в коде.

## Definition of Done
Код, миграция, unit/integration/e2e, security/ACL, API contract, UI empty/error/offline, kk/ru, accessibility, CI green, review, staging smoke, обновлены MD+HTML, release note. «Нарисовали UI» или «смержили PR» без теста ≠ готовая функция.

## Блокеры
Юридический продавец услуги, идентификация, точная политика удаления и отзывов, hosting KZ, первый город/вертикаль, provider уведомлений, Apple dev/signing, moderation staffing. Не маскировать решения фиктивными значениями.

## Дополнение к MVP v0.3 — guest-first и публикация услуг
В фазе 1 сразу проектировать **публичные read-only endpoints** без обязательной аутентификации и отдельную модель подтверждения гостевого обращения (verified guest capability). В фазе 2 обеспечить публикацию страницы профессионала и организации с публичными контактовыми каналами и настройкой видимости. В фазе 3 — реальные активные ServiceOffer с продавцом/исполнителем, доступные в каталоге. В фазе 4 — поиск для анонимных пользователей, гостевая заявка с OTP и антиспамом, последующее необязательное создание клиентского аккаунта. Приёмка MVP включает реальный сценарий «посетитель без аккаунта → поиск → просмотр услуги → звонок/мессенджер или безопасный запрос».

Реклама и спонсируемые предложения остаются P2, но поля различения органического и оплаченного результата предусматриваются на этапе проектирования выдачи. Отсутствие платного тарифа **не** препятствует базовому появлению в каталоге; отзыв/рейтинг не продаётся.

Перед реализацией гостевого запроса: согласовать юридическое основание обработки контактов, TTL/удаление гостевых данных, лимиты OTP, защиту от спама и управление заявкой по ограниченному токену. Предложение зарегистрироваться появляется после контакта и только как дополнительная ценность.

## Дополнение v0.4 — глобальная модель, локальный пилот
**Стратегия развёртывания:** архитектура, геосправочник, язык, валюты и адреса рассчитаны на разные страны с первого этапа; предложение, операции, категории и требования комплаенса запускаются поэтапно по стране/городу. «Пилот в одном городе» — ограничение на первоначальное продвижение и доступность продавцов, а не ограничение на просмотр платформы или устройство глобальной модели.

- Фаза 0: ADR по глобальным локациям, порядку определения региона, приватности IP/GPS, приоритетам ручного выбора, стране оказания услуги, онлайн-сервисам, ISO-кодам и валютам; предварительный список поддерживаемых георегионов.
- Фаза 1: геосправочник + публичные read API + preference resolver для анонимного гостя + контракты `search scope`; SSR canonical и i18n.
- Фаза 2: у профессионала и организации возможность управлять филиалами и зонами обслуживания с корректным отображением на витрине.
- Фаза 3/4: поиск по выбранному городу/области/стране/глобально, переключение без входа, фильтр online/выезд, расширение при пустой выдаче, стабильно работающие гостевые заявки.
- Фаза 5: тесты смены IP/VPN, ложного определения города, одинаковых названий городов, пересечения зон выезда, приватных адресов, локальных timezone/currency и SEO индексации. Контроль запуска и соблюдения законов по странам.

Ранние улучшения: ближайший город (без скрытого автоматического расширения), умные подсказки и локальные тренды. Не создавать тяжёлый глобальный геопоиск и платные карты до измерения реальной потребности.

## Утверждённый продуктовый срез v0.5 — минималистичные заявки и два вида страниц
**Из объёма MVP удалены:** коммерческое Quote, формальное согласование суммы, обязательная цена, обязательная календарная запись, сложная CRM-воронка и обязательные платежи. Продавец выбирает доступные способы контакта, публикует свои услуги и сам решает, принимать ли заявку. Телефон/WhatsApp — полноценный канал связи без фиктивного создания заказов.

**Добавлены в MVP:**
- Личная профессиональная страница и corporate embedded view на базе **того же** ProfessionalProfile; каждый контролирует свою часть видимости/оформления.
- Маршрутизация по источнику: личная страница → мастеру, корпоративная страница/карточка мастера → компании.
- Настраиваемые методы контакта и необязательный календарь; ручные отметки занятости и отмены записи.
- Контекстное распределение рабочих часов: компания A днём, личная практика вечером, компания B в другие дни. Известные конфликты предотвращать без раскрытия приватной информации других контекстов.
- Клиентский аккаунт для избранных страниц, подписок и собственной истории; продавец получает **честную агрегированную** статистику просмотров, заявок и зарегистрированных клиентов (не путать клики с заказами).

**Dependency gates:** сначала согласовать ADR-0003, модель seller/source_context, permissions intersection и availability; затем контракт API + Prisma migrations; затем разрабатывать две версии страниц и простой request engine, проверять E2E. Полную CRM, коммерческие стадии и платежи **не** восстанавливать без нового решения владельца.
