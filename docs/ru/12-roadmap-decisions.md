# 12. Roadmap, риски и открытые решения
> План v0.1 · Этапы зависят от проверки рынка

## Фазы
| Фаза | Результат / критерий выхода |
| --- | --- |
| 0. Discovery | 15–30 интервью с клиентами, мастерами, владельцами; подтверждены проблемы и привычные каналы |
| 1. Foundation | Auth, Person/Profile/Profession taxonomy, uniqueness, lifecycle, permissions, design system |
| 2. Marketplace MVP | Organization/Location, Affiliation, Offers, Assignments, Search, Booking, Experience, Review, Follow |
| 3. Pilot | 1 город/сегмент, модерируемые реальные визиты, измерение повторных заказов и подписок |
| 4. Retention | Уведомления о смене работы, календарь, бонусы, промокоды при согласованных условиях |
| 5. Revenue | Paid Pro/Business tools, маркированное продвижение, attribution experiments |
| 6. Expansion | Новые профессии/категории, франшизы, масштабируемый поиск, интеграции |

## Ключевой сквозной сценарий
Компания создаёт филиал и offer «стрижка». Приглашает мастера, мастер подтверждает Affiliation и отдельный ServiceAssignment. Клиент находит мастера в команде, создаёт заявку, получает подтверждение, проходит визит и пишет два отзыва. Мастер завершает связь и добавляет новый салон. Клиент по подписке видит опубликованный переезд; отзыв о мастере остаётся с мастером, отзыв о старом салоне остаётся у салона.

## Основные риски и меры
- Холодный старт рынка → начальный сегмент и профили-линки, QR для привлечения собственной аудитории мастеров.
- Конфликт мастера и компании → независимые профили, явный продавец и роли, отсутствие передачи CRM.
- Поддельные отзывы → verified experience, жалобы, антифрод, ручная модерация на пилоте.
- Избыточный конструктор → готовые шаблоны, progressive disclosure, универсальные безопасные блоки.
- Юридический риск → классификация платформы, data mapping, отдельный review регулируемых категорий.
- Неуправляемая сложность → модульный монолит, горизонтальные рамки MVP, контрактное тестирование.

## Решения, требующие подтверждения
1. Финальный бренд, домен и товарный знак (пока рабочее имя Services).
2. Первый город и целевой сегмент.
3. Кто юридический продавец по каждому виду offer и сценарий возврата.
4. Метод подтверждения визита и политика споров по отзывам.
5. Период восстановления после удаления (предложение: 30 дней).
6. Точная политика доступности истории завершённых связей.
7. Инфраструктурный провайдер и регионы хранения.
8. Платёжный провайдер и экономика платных тарифов — после пилота.
9. Перечень регулируемых профессий, доступных к публикации и заказам.
10. Набор первых отраслевых шаблонов, которые реально нужны пилоту.

## Definition of Done для фичи
Доменное правило + UI state + API contract + ACL + аудирование + локализации kk/ru + миграции/тесты + accessibility + error/empty states + обновлённая документация. «На GitHub лежит код» не равно «работает на Android/iOS».

## Аудит логических пробелов — 2026-11-01 (draft, не утверждено)
Эти вопросы **не считаются решёнными** до принятия отдельной политики или ADR. У каждого пункта должна появиться привязка к требованиям, schema/API, тесту и владельцу решения. Уже установленные продуктовые правила не менять: публичный поиск без аккаунта; явный продавец (специалист или компания); выбранный продавцом канал связи, необязательный календарь; глобальная модель с локальным поиском по умолчанию.

### P0 — блокируют проектирование заказа, идентичностей и репутации
| ID | Пробел / вопрос | Предлагаемый вариант по умолчанию, требует согласования |
| --- | --- | --- |
| GAP-01 | Где граница между обращением, сметой и юридически/операционно подтверждённым заказом? | Inquiry → Quote (если требуется) → Order со snapshot условий и согласием клиента; прямой звонок не считается автоматически заказом |
| GAP-02 | Переговоры о цене/времени и сроке действия предложения? | Версии Quote и expiry; изменение цены/работы/продавца/исполнителя после согласования требует повторного согласия |
| GAP-03 | Самостоятельный специалист работает в салоне, а компания принимает оплату: кто продавец? | ServiceOffer имеет ровно одного явно указанного продавца; место/исполнитель и платёжная сторона фиксируются отдельно; спорные схемы проходят правовой review |
| GAP-04 | Можно ли опубликовать услугу, если нет календаря и цены? | Да, при честно описанном способе обращения и условиях ценообразования (фиксированная цена, диапазон, от, по смете). Не показывать выдуманные свободные слоты |
| GAP-05 | Как совместить несколько мест работы, групповую услугу и занятость? | Общий приватный реестр реальных подтверждённых обязательств по Person/ресурсам; публиковать занятость только по opt-in; capacity/overlap правила по типу услуги |
| GAP-06 | Как происходит отмена, no-show, перенос, замена мастера и закрытие компании? | Разные reason/status и правила согласия; действующие заказы не исчезают, существенная замена требует уведомления/подтверждения |
| GAP-07 | Кто получает доступ к гостевой заявке и как гость видит статус? | Однократная/ограниченная capability по подтверждённому контакту; только продавец и делегат видят данные; ссылка/OTP не превращается в постоянную личность |
| GAP-08 | Как оформить подтверждённый отзыв при внешнем звонке без заказа в платформе? | Авторизованный автор + доказуемый ServiceExperience; без достаточных доказательств отзыв не «verified», отдельная обратная связь/жалоба возможна |
| GAP-09 | Можно ли оценить мастера и компанию по одному визиту без двойной накрутки? | Отдельные review targets, один author/experience/target, отдельные агрегаты и антифрод без смешения рейтинга компании и мастера |
| GAP-10 | Как юридически подтверждать владение компанией и профилем? | Claim + verification + журнал, защищённое восстановление при потере доступа; регистрация аккаунта ≠ доказательство прав на бизнес/лицензию |
| GAP-11 | Что делать со сменой работодателя и будущими заявками? | История связей не стирается; новые назначения закрываются; по незавершённым заказам применяется политика продавца и согласие клиента при замене |
| GAP-12 | Как изменять каноническую профессию, если она была объединена/разделена? | Стабильные идентификаторы, controlled alias/merge policy, migration profile ownership and reviews; не создавать автоматически второй профиль |
| GAP-13 | Как удалить аккаунт, сохраняя необходимую историю заказов и достоверные отзывы? | Разделить стирание PII, анонимизацию публичных данных и законное retention; срок 30 дней пока не утверждён |
| GAP-14 | Какие страны и регулируемые профессии разрешены для публикации и заказа? | Глобальный поиск, но country/category capability flags; юридический gate до включения операций/рекламы по стране |

### P1 — важные продуктовые и операционные решения
| ID | Пробел / вопрос | Рекомендуемое направление |
| --- | --- | --- |
| GAP-15 | Может ли задача иметь нескольких исполнителей, этапы и частичное выполнение? | Assignment many-per-order и milestones как расширение; не принуждать все категории к одной модели визита |
| GAP-16 | Должен ли мастер указывать «свободен/занят» публично? | Только его настройка: hidden, general_status, schedule, bookable_slots; отсутствие календаря не снижает рейтинг |
| GAP-17 | Кто управляет претензиями и какую ответственность принимает платформа? | Внутренние report/case/appeal и понятный scope модерации; не обещать юридический арбитраж без отдельной политики |
| GAP-18 | Что именно значит цена: фиксированная, «от», диапазон, смета, налоги, валюта? | Явные price_kind, currency ISO 4217, налоги/условия, срок действительности Quote; запрет скрытой подмены цены |
| GAP-19 | Как не дать накручивать объявления, подписки и отзывы через бесплатные аккаунты? | Проверка права владения, rate limits, spam/moderation, дедупликация, защита SEO и поисковой выдачи, прозрачная реклама |
| GAP-20 | В каких случаях профили и службы регистрируются как разные юрлица/филиалы/бренды/франшизы? | Разные entity kinds и ownership/branch hierarchy; историю прав не терять при продаже/реорганизации |
| GAP-21 | Как собирать статистику звонков/мессенджеров, не выдавая клики за заказы? | Считать только contact_click; verified fulfilment requires separate evidence; не тайно перехватывать частные контакты |
| GAP-22 | Как связаны языки, страна поиска, право оказания услуги, валюта и часовой пояс? | Независимые параметры; зона обслуживания у Offer; юрисдикция договора не определяется автоматически IP |
| GAP-23 | Как разделить публичный кеш и приватные заявки/OTP, когда сайт вырастет? | Modular monolith+Postgres, CDN для публичного SSR/media, no-store private data, индексы, пагинация и профилирование; микросервисы позже |
| GAP-24 | Какие поля/блоки конструктора можно делать обязательными по категории? | Минимальный общий набор, типизированные schema-versioned blocks и отраслевые шаблоны, безопасный renderer без HTML/script |
| GAP-25 | Как избежать конфликтов cookie/mobile auth и утечек в глобальных интеграциях? | Отдельные adapters, resource ACL/IDOR tests, CSP, секреты вне клиентского бандла, minimization data and audit |

### Вопросы, которые должен утвердить владелец продукта до полноценной разработки
1. Может ли продавец оставить **только телефон/мессенджер** без заявок внутри Services, или хотя бы один in-platform канал обязателен?
2. Будет ли **согласование заказа** внутри платформы обязательным для «подтверждённого визита», или допустим независимый QR/код подтверждения офлайн-визита?
3. Должна ли платформа поддерживать **сметы/переговоры и поэтапные работы в MVP**, или сначала только простые запросы и записи?
4. Кто подтверждает **исполнителя заказа** при замене мастера у компании, и какие условия требуют согласия клиента?
5. Какие **категории и страны** активны на старте? Глобальная видимость каталога ≠ право продавать любую услугу в любой стране.
6. Как трактовать услуги **арендатора рабочего места**: самостоятельный продавец, клиент салона или выбор на каждый ServiceOffer?
7. Нужно ли платформе **посредничать в спорах по качеству**, или только принимать жалобы на контент/профили и хранить историю обращения?

### Рекомендация по процессу
Начать foundation/дизайн-систему можно. До реализации booking/quotes/reviews и Prisma-ограничений утвердить GAP-01..14, затем обновить главы 02–06, 15–18, OpenAPI, диаграммы и тесты. До открытия стран провести отдельный юридический review, включая конкретное хранение и трансграничные потоки персональных данных. Никакая схематическая или Markdown-проверка не доказывает законность либо работоспособность.
