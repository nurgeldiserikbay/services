# ADR-0010 — безопасная материализованная CompanyProfessionalView

**Статус: PROPOSED PERFORMANCE/PRIVACY DESIGN.** Уточняет главы 03/05 и ADR-0007. Не превращает технический кэш в источник прав.

## Требование
Публичный запрос корпоративной карточки не должен вычислять пересечение длинных схем прав на каждый блок. Используется `PublishedCompanyProfessionalView` — денормализованный публичный whitelist только разрешённых полей и компонентов, сформированный из:
`professional.masterAllowedFields ∩ company.selectedFields ∩ platformPolicy` + действующая `Affiliation` + права публикации конкретного медиа.

**Самое важное:** асинхронный воркер и CDN-инвалидация сами по себе не обеспечивают *немедленного* отзыва разрешения. После изменения allowlist или завершения Affiliation старый payload не должен возвращаться даже при очереди воркера, сбое CDN или stale-while-revalidate.

## Согласованный протокол публикации

1. Транзакция изменения прав увеличивает монотонную `visibilityRevision` пары affiliation/view, устанавливает `publicationState=STALE` (или `REVOKED` при прекращении), фиксирует событие outbox для пересчёта и инвалидации; в той же транзакции изменения новых разрешений вступают в силу.
2. На `GET` публичной read-модели сервер либо сверяет дешёвый version/state marker, либо читает актуальный компактный `PublicationGuard` (из устойчивого strongly consistent источника), прежде чем отдать кэшированный JSON. Если rev не совпадает, **не отдаёт старый payload**: отвечает `404`/безопасным пустым представлением (или пересчитывает синхронно из проверенных разрешений). Для отзыва — fail closed.
3. Воркер по outbox (at-least-once) пересчитывает **строго из актуальных разрешений**, формирует готовый sanitized JSON с `sourceRevision`, условно публикует только если ревизия ещё текущая, атомарно переключает marker на `READY`; старый job не может перезаписать новую публикацию.
4. CDN использует revisioned URLs/cache keys или краткий TTL, purge по surrogate-key и защиту от stale: запрещено кэшировать персональные/приватные сведения; revocation критически требует пропуска через server guard или uncacheable proxy, а не надежды только на eventual purge. На этапе пилота допускается `no-store` для embedded карточек, если мгновенная инвалидация ещё не доказана.
5. Выдаваемый JSON **не содержит скрытых полей**, даже с `visible:false`; кэширование должно быть одинаково безопасным для SSR/API, изображений/thumbnail, поискового индекса, OpenGraph и mobile.
6. Публичная read-модель не даёт новых прав: запрос на услугу, управление карточкой и компания/мастер ACL всегда проверяются по первичным данным; seller identity корпоративной заявки остаётся организацией.

## Состояния и сбои
`READY | STALE | REVOKED`. Задача воркера может повторяться, события могут приходить вне порядка; version fence и идемпотентность обязательны. При недоступности guard storage отдавать закрытое представление, не старый кэш. Метрики: lag пересчёта, stale rejected, purge errors, revocation exposure; audit без PII.

## Приёмка
- Изменение разрешения удаляет поле из API/SSR/CDN сразу после commit, даже при остановленном worker.
- Противоположный порядок событий rev N+1 и rev N не возвращает старую публикацию.
- Закрытие affiliation/отзыв согласия немедленно скрывает публичную карточку, но не удаляет pending/accepted заявки (ADR-0007).
- Компания не может расширить поля вне allowlist мастера; нельзя получить через старые media URL.
- N+1 запросов без JSON intersect: измерить P95/P99 по фактическим страницам; не вводить дополнительную инфраструктуру, пока нагрузка этого не требует.

**Статус внедрения:** архитектурное решение, требуется API/DB/worker design, нагрузочные и security tests.
