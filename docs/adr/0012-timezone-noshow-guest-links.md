# ADR-0012 — изменение часовых поясов, спорная неявка и guest deep links

**Статус: PROPOSED — общеплатформенный технический контракт.** Правила одинаково применяются к личным услугам, компаниям, вебу и мобильному приложению. Это не временная MVP-оговорка.

## 1. Время услуги, TZDB и защита согласованной договорённости

**Источник истины — подтверждённая договорённость**, а не текущее отображение локальных часов устройства клиента.

Для каждой подтверждённой ревизии времени хранить:
- `local_start` — неизменённое исходное wall-clock время услуги (дата и часы без offset);
- `iana_timezone` — канонический IANA zone ID, например `Asia/Almaty`;
- `utc_start` и `utc_end` — вычисленные конкретные instant;
- `utc_offset_seconds_at_confirmation` и `tzdb_version` (если доступна), `agreement_revision`, `confirmed_at`;
- deadline policy revision, effective UTC deadline и временную метку подтверждения обеими сторонами.

Для DST overlap с повторяющимся локальным временем клиент/продавец выбирает конкретный offset; для DST gap (несуществующее локальное время) сервер требует выбрать другое время. Нельзя молча нормализовать 02:30 в 03:30.

**Сравнение дедлайна выполняется по UTC-instant** — переводить `now()` в локальную зону ради сравнения неправильно и может создать неоднозначность. IANA/local/offset хранятся для корректного показа, сверки и обнаружения обновления правил.

Если после подтверждения обновилась TZDB и исходное local wall-clock время теперь соответствует другому UTC instant, сервер ставит `schedule_reconciliation_required` и уведомляет обе стороны. Старый UTC момент не переносится автоматически; изменение конкретного instant требует нового подтверждения (ADR-0006). Пока разночтение не разрешено, **customer reliability penalty и no-show автоматически не начисляются**. Приватные audit records сохраняют исходные instant и zone, но публичное UI показывает предупреждение. Все согласованные ревизии остаются неизменными.

CAN-T16 тесты: изменение правил Asia/Almaty, spring-forward gap, autumn fold, разные TZDB версии backend/client, 24h boundary, созданная за месяцы запись и повторное подтверждение после обновления; проверять одинаковый результат на web/native и независимость от device timezone.

## 2. No-show — заявление, а не автоматический приговор

Сервисное `NoShowClaim` не является новым `RequestStatus`. Его процесс: `FILED -> AWAITING_CUSTOMER -> DISPUTED/UNCONTESTED -> UNDER_REVIEW -> CONFIRMED/REJECTED/EXPIRED`. `UNCONTESTED` **не означает доказанное отсутствие**.

- Продавец может подать заявление только для своей `ACCEPTED` заявки с подтверждённым временем, **не раньше scheduled_start_at_utc + 15 минут** по серверному времени; в ожидании согласования/изменения времени или TZ reconciliation кнопка заблокирована. Дополнительное окно подачи (например 48 часов) конфигурируется с версией правила.
- Подача создаёт claim с actor, seller identity, request/schedule revision, доказательствами, audit trail и outbox событием. Нельзя прямо установить `ReliabilityEvent.status=EFFECTIVE`. За одну пару request/customer доступен максимум один активный claim (idempotency).
- Клиент получает уведомление с безопасной ссылкой на просмотр (без bearer token) и действиями «Я был/провайдера не было», «Меня не было», «Оспорить». Каналы зависят от подтверждённых контактов и предпочтений; отправка push/SMS не гарантируется.
- При возражении дело направляется на рассмотрение в отдельную ограниченную очередь `services-admin`, без уменьшения customer reliability до вердикта; модератор может запросить доступные минимизированные доказательства обеих сторон.
- При отсутствии ответа **молчание клиента не трактуется как признание**. Автоматический отрицательный reliability event не создаётся; дело может быть закрыто без санкции или рассмотрено по достаточным независимым основаниям согласно review policy.
- Только решение авторизованного модератора или формально проверенный независимый механизм выпускает `ReliabilityEvent` с `EFFECTIVE`, versioned reason и возможностью апелляции. Отзыв/отмена решения создаёт `REVERSED`/корректирующее событие и пересчитывает score. Компания несёт ответственность за действия оператора, но нельзя перенести вину на клиента без фактов.
- Предотвращать двойной учёт одного факта как отмены и no-show, запретить backdating и unilateral schedule change. Для guest без зарегистрированного customer score — никакого постоянного штрафа будущему аккаунту.

Транзакционный worker использует outbox, leasing, retry/dead-letter, optimistic version fencing, детерминированный dedupe key. Clock и deadline берутся только с сервера; при любой гонке с cancel/reschedule/finish policy оценивается заново в транзакции перед переходом. Логи не включают контакты и свободный текст доказательств.

Тесты: заявление в +14:59 отклонено, в +15:00 допустимо; pending/cancelled/no agreement запрещены; два одновременных claim не дублируются; спор замораживает score; клиент не отвечает — нет автоматического взыскания; поздняя доставка уведомления не меняет права; appeal reverses; оператор чужой организации получает 403.

## 3. Гостевые ссылки и Capacitor

Гостевая web cookie не переносится в OS Secure Storage установленного приложения, и приложение не вправе использовать отсутствие native guest token как основание показать чужие данные.

Все внешние уведомления о гостевой заявке ведут на **обычный HTTPS recovery route** (`/guest-requests/recover`) без bearer capability в query, fragment или path. У ссылки могут быть неавторизующие UI-параметры (например локаль), но её открытие **никогда не раскрывает** заявку до OTP или до действительной одно-request web session. Отдельные ссылки на cancel с `?token=...` запрещены даже при `noindex`.

- В Android App Links/iOS Universal Links исключить `/guest-requests/*` из native route association, где платформа поддерживает исключения. Проверить фактическое поведение на каждой OS; браузерный fallback обязателен, нельзя считать фильтр универсально гарантированным.
- Если ОС всё же открыла приложение, показывать безопасный выбор «Продолжить в браузере» или native OTP recovery; **не** пробовать передать браузерные cookies в нативный токен. Никакой 403 как конечный UX без восстановления.
- Guest web session: Secure, HttpOnly, SameSite cookie, server-side request scope, CSRF на мутации, no-store/anti-index headers для приватного контента; `robots noindex` не заменяет авторизацию. При потере cookie — восстановление только через подтверждение первоначального контакта (ADR-0008).
- Никогда не помещать в журналы, email/SMS URLs, analytics или deep link intents guest capability/OTP. Выход из гостевого контекста и отзыв capability немедленно прекращают доступ.

## Критерии sign-off

1. Единый тестируемый instant/zone/offset контракт и ревизии подтверждения.
2. Реализация no-show как отдельного claim с review, audit, idempotency и отсутствием автоматической санкции по одному заявлению.
3. Проверенные на Android/iOS устройствах guest browser links, не содержащие секретов, плюс recovery.
4. Негативные DB/API/ACL тесты и versioned правила для всех поддерживаемых рынков, не только одного пилота.

**Примечание:** документ задаёт контракт для промышленной реализации; миграции, worker, UI и тесты пока должны быть реализованы и проверены отдельно.
