# ADR-0006 (proposal) — согласование времени без обязательного календаря

**Статус: PROPOSED / implementation contract, 2026-11-02.** Не меняет принятый ADR-0003 (простые заявки) и ADR-0004 (отмена/надёжность). Требует review до реализации.

## Цель
Сделать дату понятной обеим сторонам, не превращая сервис в CRM. Клиент оставляет простую заявку; продавец принимает или отклоняет. Общение по телефону/WhatsApp разрешено, календарь добровольный. Для ограничения отмены по времени требуется **доказуемое согласование времени**, а не предположение системы.

## Четыре независимых измерения
- **Статус заявки:** `PENDING`, `ACCEPTED`, ... отдельные статусы `CANCELLED_*`. Согласование времени не вводит дополнительных `RequestStatus`.
- **Пожелание:** `desired_start_at` в заявке — не согласование, не бронь, не источник санкции.
- **Договорённость о времени:** `ScheduleAgreement` с revision, proposed slot, initiator, confirmation actor/time; `NONE | PROPOSED | CONFIRMED` как отдельный schedule state. Исторические revisions не удалять.
- **Занятость:** `BusyBlock` (если календарь включён и известен исполнитель) — техническая блокировка ресурса, не подтверждение согласия клиента.

## MVP: сценарии
1. Клиент создаёт заявку, может указать желаемое время, но не обязан. Продавец может принять без времени: заявка `ACCEPTED`, schedule `NONE`, отмена клиента без автоматического late penalty.
2. Если перед принятием стороны уже договорились вне платформы, продавец вводит дату и предлагает её в системе. Для **registered** клиента подтверждение в личном кабинете; для **guest** — только через его scoped verified request capability. Нельзя подтверждать через публичную ссылку.
3. Предложение даты меняет schedule state на `PROPOSED` и уведомляет вторую сторону. Не изменяет согласованную дату, cancellation snapshot или penalty.
4. Клиент нажимает «Подтвердить время» — schedule `CONFIRMED`; сервер атомарно проверяет доступность известного мастера, связывает BusyBlock и фиксирует новый cancellation snapshot. Продавец видит подтверждение. Сервер показывает deadline на основе ADR-0004; если день уже начался, нельзя задним числом ухудшить рейтинг клиента.
5. Клиент отклоняет предложенную дату — предложение закрывается, заявка остаётся `ACCEPTED`, последнее **ранее подтверждённое** время остаётся историческим. Если инициатором изменения является продавец, прежний deadline перестаёт служить основанием клиентского штрафа, пока не будет новое соглашение или явное восстановление прежнего времени обеими сторонами.
6. При переносе по инициативе клиента продавец тоже должен подтвердить новый слот. Общее правило: инициатор предлагает, **вторая сторона подтверждает**; нельзя автоматически подписать соглашение от её имени.
7. Если предложений несколько — сохраняется одна активная proposal revision на заявку; новое предложение отменяет прежнее только с уведомлением и optimistic version check.
8. При отмене/отклонении/завершении заявки новое согласование запрещено; pending proposal закрывается. Любая отмена всё равно создаёт два notification intent по ADR-0004.
9. Если продавец использует только телефон/WhatsApp и не хочет фиксировать время в системе, платформа не утверждает, что запись подтверждена и не применяет автоматическую late-пенализацию клиента.
10. Услуга может завершиться без date agreement; завершение — отдельный transition продавца, не автоматическое событие по часу.

## Состояния предложения

| From | Event | To | Side effects |
| --- | --- | --- | --- |
| NONE/CONFIRMED | propose by seller/customer | PROPOSED | Revision + outbox; прежнее подтверждение хранится |
| PROPOSED | confirm by recipient | CONFIRMED | Проверка слота и actor ACL, snapshot и busy в одной транзакции |
| PROPOSED | decline by recipient | NONE или предыдущий CONFIRMED, но penalty suspended при seller-initiated reschedule | Outbox, без новых санкций |
| PROPOSED | supersede by authorized participant | PROPOSED new revision | Старое предложение нельзя подтвердить |
| PROPOSED | cancel request | CLOSED (derived) | По правилам cancellation, без второго побочного штрафа |

**Уточнение:** это проектная state machine для времени, не новые значения Prisma `RequestStatus`. Если proposal применяется после принятия, request остаётся `ACCEPTED`; если дата нужна до принятия, продавец сначала принимает и затем отправляет предложение. Договорённость по телефону без явного подтверждения через платформу не основание для штрафа.

## Privacy, fairness and safety
- Не показывать бизнесу личные подробности занятости мастера в другом контексте.
- Предложения содержат UTC instants + IANA timezone; backend отклоняет DST nonexistent local times и требует явное offset/disambiguation для fold.
- Коды `SCHEDULE_PROPOSAL_STALE`, `SLOT_CONFLICT`, `SCHEDULE_CONFIRMATION_REQUIRED`; статус 409 при конкурентном переходе, 403/404 при чужом объекте.
- Idempotency-Key на предложении и подтверждении; CAS по version. Нельзя записывать второй snapshot без версионирования: обновление effective snapshot только после подтверждения, исторические revisions в `ScheduleAgreement`.
- Если новый дедлайн уже прошёл к моменту подтверждения, клиент получает минимум grace ADR-0004, не наказание за немедленную отмену.
- Сохранить actor, timestamp, revision, источник подтверждения и время отправки уведомления; не сохранять OTP/secret в audit.

## Контракты перед реализацией
- Data: отдельная история `ScheduleAgreement`, active proposal revision, статус согласования и отметка приостановки penalty. **Не переписывать** existing `CancellationSnapshot` без review миграции.
- API: `POST /requests/{id}/schedule-proposals`; `POST /requests/{id}/schedule-proposals/{proposalId}/confirm`; `.../decline`, все с Idempotency-Key; возвращать schedule revision и current request version.
- Existing `PATCH /requests/{id}/schedule` сейчас формулируется как отметка продавца после внешнего согласования; **deprecated for automatic agreed-time semantics**. В будущем либо удалить, либо разрешить только non-penalizing note после отдельной миграции.
- UI: две даты (пожелание vs подтверждено), явные две кнопки «Подтвердить» и «Не подходит», и понятный дедлайн только после подтверждения.
- QA: race confirm/cancel; duplicate proposal; proposal superseded; schedule without selected performer; time-zone DST; anonymous guest capability; seller reschedule after deadline; no reliability penalty without confirmation.

## Незакрытые вопросы (не домысливать кодом)
Ретенция истории предложений и правило удаления PII; максимальная длительность/временной горизонт; политика блокировки ресурса до подтверждения (по умолчанию **никакого soft hold**); UX получения гостем подтверждения без обязательного аккаунта. Тесты, миграции и юридический review обязательны.
