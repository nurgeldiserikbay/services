# ADR-0008 — защита гостевого OTP, восстановление доступа и web-сессии

**Статус:** PROPOSED SECURITY DESIGN. Уточняет ADR-0005; не меняет продуктовый принцип отсутствия обязательной регистрации.

## Модель угроз

Публичный endpoint для создания OTP может вызвать: SMS/email bombing конкретного человека, исчерпание бюджета провайдера, перебор кода, массовые заявки продавцам, enumeration зарегистрированных контактов и утечку доступа через URL, клиентскую аналитику, браузерную историю или логи шлюза.

## Защита выдачи OTP

1. На всех guest challenge endpoint: token-bucket и sliding window по **хешу нормализованного контакта**, IP/подсети, краткосрочному device/risk identifier, offer/seller и глобальному бюджету канала. Предлагаемый стартовый порог: **не более 3 отправок на контакт за 15 минут**, с отдельными лимитами на IP/подсеть, destination, день и продавца; численные лимиты конфигурируются по провайдеру и проверяются нагрузочно. IP не является идентичностью: NAT и мобильные сети могут делить/менять адрес.
2. Повторные вызовы в пределах срока жизни challenge **не должны автоматически отправлять новый SMS**; resend — с cooldown и ограниченным числом отправок. Отвечать унифицированным статусом без раскрытия существования контакта; audit причин ограничения хранить приватно.
3. **Адаптивный CAPTCHA/turnstile** только при росте риска (аномальная скорость, подозрительная репутация, превышение бюджета), а не обязательный на каждом обычном запросе. Проверка CAPTCHA на сервере; не считать её заменой rate limiting, OTP или контролю стоимости.
4. Глобальные и per-provider **spend ceilings**, circuit breaker, аварийное отключение SMS, очередь с ограниченной скоростью, дешёвый email fallback только с согласия пользователя. Не создавать неограниченные challenge записи; TTL cleanup, индексы, квоты.
5. Создание гостевой заявки требует успешно подтверждённого контакта, идемпотентности и deduplication per destination/offer; ограничивать активные обращения и spam-нагрузку конкретного мастера. Нельзя создавать `PENDING` от одного только запроса на отправку OTP.
6. Код: hash/HMAC (в зависимости от генерации и энтропии), краткий TTL, лимит проверок, атомарное поглощение, защита от replay и constant-time проверка. Отделить challenge для первой заявки, восстановления и согласования времени, не переиспользовать purpose.
7. **Fingerprint не является обязательной криптографической привязкой токена.** Его стабильность и приватность ограничены, особенно на мобильных устройствах и при смене браузера. Использовать минимальные risk-сигналы с retention/consent, исключить кросс-сайтовое слежение; владение контактом и точный request scope являются основой доступа.

## Хранение guest capability и восстановление

**Веб:** после успешного OTP сервер устанавливает host-only cookie `__Host-services_guest_session` с `Secure; HttpOnly; Path=/; SameSite=Lax` (Strict — если UX совместим), коротким TTL, серверной ротацией/отзывом. Cookie содержит непрозрачный session id или подписанный секрет, а не открытый request id / raw capability. В server-side session хранится разрешённый request UUID и точный набор scopes. Ответы с приватным статусом — `Cache-Control: no-store`; CSRF-защита обязательна для мутаций. Для native-клиента использовать отдельный защищённый storage адаптер, не web cookie по умолчанию.

**Восстановление:** страница `/guest-requests/recover` запрашивает контакт, подтверждённый при создании заявки, и выполняет новый OTP challenge с отдельным purpose. После проверки сервер показывает только **заявки, принадлежащие этому подтверждённому контакту**, с минимальным набором идентификационных данных для выбора; затем создаёт новую short-lived session, привязанную к выбранной заявке. Если номер уже перевыпущен другому владельцу, требуется защита от account recovery takeover: срок жизни гостевых обращений, дополнительные проверяемые признаки или ручная процедура по риску/сроку. Не считать OTP доказательством неизменной личности во времени.

**Ссылки:** не отправлять bearer capability в SMS/email URL. Разрешена только обычная ссылка на страницу восстановления без секрета, например `/guest-requests/recover`, после открытия — новый OTP. Не включать токен в query, fragment, referrer или клиентские логи.

**Доступ:** `guest_session` разрешает чтение/отмену только указанной заявки, подтверждение времени требует отдельно выданного `MANAGE_SCHEDULE` после повторной проверки. Обновление scope не происходит автоматически. При терминальном состоянии заявки ограничения и отзыв должны применяться сервером.

## Backend, API и операционные требования

- Описать отдельные endpoints `POST /guest-requests/recovery/challenges` и `POST /guest-requests/recovery/challenges/{id}/verify` с generic ответами, CSRF/session semantics и rate-limit errors. Это **контрактное предложение**, не реализованный маршрут.
- Отправка challenge и расход провайдерского бюджета должна быть атомарно резервируемой в защитном ledger или согласованной очереди; при таймауте нельзя повторно взимать отправку. Наблюдаемость: attempted/sent/rejected/provider-cost, отдельно от реальных customer requests.
- Провести abuse tests: 1000 concurrent challenge requests, one contact via many IPs, many contacts from one IP, bad captcha, provider outage, reused OTP, SMS budget exhaustion, duplicate pending requests, stolen/expired cookie, CSRF, mismatched request id, number recycling.
- Привязка по IP/fingerprint не должна блокировать легитимного пользователя при переключении Wi-Fi/LTE или shared NAT; использовать их для risk scoring и дополнительных вызовов OTP, а не безусловного лишения доступа.
- Текст Privacy/retention и локализацию kk/ru обновить до публичного запуска. Не включать contact, OTP, secret, session id в логи/trace/analytics.

## Решение для MVP

Минимально: контактный лимит и глобальный бюджет SMS, cooldown/resend, CAPTCHA по риску, запись заявки **после** OTP, request-scoped guest cookie, восстановление через новый OTP и запрет секретных ссылок. Более тяжёлый fraud detection — только при измеренной необходимости.
