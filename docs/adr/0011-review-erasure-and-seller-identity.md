# ADR-0011 — отзыв после стирания Person и стабильная идентичность продавца

**Статус: PROPOSED DATA-MODEL DECISION.** Требуется review миграций и применимого privacy/retention права перед реализацией.

## Проблема: Review и стирание автора

Сейчас `Review.authorPersonId` обязателен и ссылается на `Person` через `onDelete: Restrict`. Это препятствует физическому удалению Person, пока существуют отзывы. При этом отзывы компании не должны удаляться только потому, что клиент или отдельный мастер закрывает свой профиль.

### Инвариант анонимизации автора

1. `Review.authorPersonId` и отношение `author` становятся nullable. После допустимого **окончательного** стирания Person система анонимизирует опубликованный отзыв: `authorPersonId = NULL`, публичный display name/avatar удаляются, `comment` очищается либо проходит доказуемую PII-redaction с консервативным default = NULL. Звёзды, review ID, объект оценки и статус достоверности сохраняются *только* при наличии правового основания, политики retention и отсутствия риска обратной идентификации.
2. `verifiedExperienceSnapshot` может быть необратимой технической меткой «проверяемый опыт на момент отзыва», **не** копией `ServiceExperience` с клиентским ID или хешом телефона. Простого boolean недостаточно для антифрода: для внутреннего аудита допустима отдельная минимизированная retention-bound доказательная запись с защищённым ACL. Не публиковать уникальный experience ID как link на клиента.
3. Удаление профиля мастера отличается от стирания Person автора: прекращение профессиональной страницы не удаляет ни отзывы, ни корпоративную историю компании. Для удалённого target мастера необходим **непубличный tombstone/архив профиля**, пока на него ссылаются законно хранимые отзывы, заявки, начисления надёжности. `ProfessionalProfile.status = ARCHIVED` снимает публикацию; это не физическое удаление и не освобождает `unique(personId,professionId)`. Стирание владельца Person требует отдельно переосмыслить FK/tombstone, обезличивание целевой стороны, сроки хранения и правило возможной повторной регистрации.
4. Репутация мастера и компании не смешивается. Старые отзывы о компании остаются у компании; анонимизация клиента не переводит их на мастера или наоборот. Публикация агрегата должна подавлять малые выборки, позволяющие восстановить автора.
5. Заявки и `ServiceExperience` могут сохранять связь с автором после `Review.authorPersonId = NULL`; поэтому **анонимизация одного Review сама по себе не является полным стиранием Person**. Нужна графовая процедура data-subject erasure для всех таблиц, медиа, outbox, поискового индекса, логов и backup согласно retention exceptions.

### Транзакция erasure

Установить lifecycle `pending_deletion -> erased` только после проверки разрешённых обязательств. В одной координированной процедуре закрыть личный доступ, отозвать токены, удалить/обезличить комментарии и атрибуты автора, зафиксировать idempotent progress/audit без PII. Background deletion для backups/media/index сопровождается процессом проверяемого завершения; не обещать атомарное уничтожение распределённых копий в одной DB-транзакции. Повторный запуск безопасен.

## Проблема: полиморфный продавец ServiceOffer

Текущая пара `professionalId?` / `organizationId?` с XOR CHECK и двумя настоящими FK **валидна и понятна для MVP**. Она не нарушает referential integrity, хотя требует явного branching ACL. Но ветвления должны быть централизованы в едином `SellerAccessPolicy` / domain resolver (seller type, seller UUID, current memberships, revocations, offer context) и проверяться на каждом приватном запросе.

### SellerIdentity — возможное развитие, не обязательная замена сейчас

`SellerIdentity(id, kind, professionalId?, organizationId?)` также требует XOR CHECK, уникальных ограничений, отдельной миграции, backfill, обновления всех FK и request seller snapshots. **Один FK на ServiceOffer не устраняет полиморфизм и не заменяет ACL/IDOR**. Называть сущность `BillingAccount` неуместно: Services не хранит платежи и не управляет ценой.

Если профили/организации станут участниками множества seller-ориентированных таблиц, можно утвердить `SellerIdentity` отдельно и реализовать в expand/migrate/contract:
1. Создать identity table и ограничения; заполнить для существующих профилей/организаций, не меняя продавца исторических заявок.
2. Добавить nullable `sellerIdentityId`, backfill, проверить consistency с существующей XOR-парой; двойная запись до готовности клиентов.
3. После data/API migration сделать единый FK обязательным и убрать дубли только после проверки ACL и индексов.

**На данном этапе решение:** сохранить два nullable FK + PostgreSQL XOR и единый backend ACL resolver до появления измеренной потребности в `SellerIdentity`. Это предотвращает рискованный рефакторинг ради абстракции без доказанной выгоды.

## Проверки

- Удаление автора не удаляет отзыв компании; `author_person_id` допускает NULL, текст очищается, оценка сохраняется только по retention policy.
- Нельзя восстановить автора из `verifiedExperienceSnapshot` или публичного ID; негативные privacy тесты на поисковый индекс/логи/агрегаты.
- Архивирование мастера не нарушает `unique(person_id,profession_id)`, не меняет seller у уже принятых корпоративных заявок.
- Создание offer с обоими seller FK или без обоих — отказ DB; корректный seller FK с чужой организацией не предоставляет ACL.
- Тесты reseller spoofing, IDOR, revoked OrganizationMember и company-view контекста.
- Миграции обязательны на реальном PostgreSQL; схема ТЗ не утверждается как уже развёрнутая.
